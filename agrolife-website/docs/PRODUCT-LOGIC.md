# AgroLife: логика рабочего пространства

## Каталог и план культуры

В первой версии каталога только три культуры:

| Культура | Логика плана |
| --- | --- |
| Малина | Осмотр после посадки → полив после укоренения → подкормка → осмотр побегов → полив перед цветением → подкормка в цветение → проверка завязей → контроль сбора |
| Клубника | Осмотр после посадки → полив → подкормка после укоренения → осмотр цветения → полив налива ягод → контроль сбора |
| Смородина | Осмотр после посадки → полив → весенняя подкормка → осмотр цветения и завязей → полив налива ягод → контроль сбора |

Числа в плане — дни после даты посадки и стартовый сценарий интерфейса. Они не являются агрономическим назначением: перед рабочим запуском их нужно проверить по региону, сорту, погоде и технологии выращивания. В календаре каждая работа показывает тип — осмотр, полив, удобрение или сбор.

## Основной путь

**Участок → наблюдение → задача → выполнение → история.**

Пользователь выбирает культуры в профиле. Затем добавляет поле, выбирает одну из доступных культур и указывает площадь и дату посадки. AgroLife сразу строит план по выбранной культуре. После выхода на участок фермер фиксирует фактическую стадию, состояние растений и заметку. Следующую работу он может добавить или перенести вручную. В обзоре отображаются актуальные задачи и просрочки.

## Единые правила

| Объект | Источник данных | Правило |
| --- | --- | --- |
| Общая площадь | Поля | Сумма площадей в гектарах |
| Стадия | Последний осмотр | Факт со слов пользователя; не вычисляется по дням |
| Состояние | Последний осмотр и задачи | Просрочка либо отмеченная проблема требуют внимания |
| Полоса прогресса | Задачи участка | Выполненные / все назначенные |
| Просроченная работа | Дата и статус задачи | До сегодняшнего дня и ещё не выполнена |
| Приоритет | Выбор пользователя | В пределах даты важные задачи идут первыми |
| Последний осмотр | Дата наблюдения | При одинаковой дате — более поздняя запись |
| Объём воды | Площадь и введённая норма | Га × 10 000 × л/м²; затем / 1 000 для м³ |
| Ответ Асыл | Текущее состояние кабинета | Локальные сценарии, без внешней модели |

Выполнение задачи не означает, что обнаруженная на поле проблема исчезла. Чтобы отметить изменение состояния, нужно записать новый осмотр. Перенос работы меняет её дату без создания дубля. Изменение поля сохраняет привязанные задачи и наблюдения.

Подготовительные задачи можно планировать до посадки; фактические осмотры растений — только начиная с даты посадки. Будущая дата посадки допускается. Смена культуры в настройках не удаляет старую историю — в полноценной версии культуры стоит относить к отдельным сезонам.

## Расчёт и задача на полив

1. Выбор участка подставляет площадь и культуру.
2. Пользователь проверяет норму. Начальные числа — примеры интерфейса.
3. Смена единиц га/м² пересчитывает значение площади, сохраняя её размер.
4. Изменение любого параметра инвалидирует результат и убирает кнопку планирования.
5. После расчёта кнопка открывает форму задачи. В названии фиксируются объём, площадь и норма. Пользователь выбирает время и подтверждает добавление.
6. Расчёт не равен назначению. Погода, почва и потери не моделируются.

## Сохранение

`core.js` содержит общую логику и возвращает новое состояние. `app.js` проверяет состояние, сохраняет его и обновляет экраны. Формы используют ту же валидацию, что и загрузка данных.

Данные версии 0.1 мигрируют без изменения пользовательских дат. Вымышленные стадии и проценты не переносятся в журнал наблюдений. При ошибке чтения исходная запись остаётся нетронутой. При ошибке записи интерфейс предупреждает, что изменения существуют только в текущем сеансе.

Это локальная модель прототипа. Для рабочего сервиса понадобятся API, серверная база, авторизация, резервное копирование и разрешение конфликтов между устройствами. Последующая интеграция должна сохранить приведённые правила, а не дублировать их несовместимыми формулами.
